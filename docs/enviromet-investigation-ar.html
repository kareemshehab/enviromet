النتيجة المقترحة: الاستمرار بالبنية الحالية لموقع EnviroMET، مع Vercel Pro وSupabase Pro كبداية للإنتاج بميزانية أساسية تقديرية 45 USD / month لمطور واحد وقاعدة Micro واحدة. إدارة عدة مواقع من CMS واحد ممكنة، لكنها تحتاج مرحلة تطوير وترحيل مستقلة. تحسينات SEO موجودة في الكود وتحتاج نشرًا بالإعدادات الصحيحة لتؤثر على الموقع العام.

المشروع الحالي

حسب package.json المشروع يستخدم Next.js 16.3.3 وReact 19.2.6 وPayload CMS 3.90.2. واجهة الموقع ولوحة الإدارة وواجهات API تعمل من نفس التطبيق. البيانات محليًا في SQLite، وفي الإنتاج يستخدم إعداد Payload قاعدة PostgreSQL عندما يكون DATABASE_URI مضبوطًا.

المحتوى موزع على Pages وServices وProjects، مع Media وShared Sections وPage Templates وEnquiries وUsers. الإعدادات العامة موجودة في Header وFooter وSite Settings وSolution Template. الموقع يدعم الإنجليزية والعربية؛ المسار العربي يبدأ بـ/ar.

الصور والفيديوهات في إعداد الإنتاج تُرفع إلى Vercel Blob، وليس إلى Supabase Storage. Supabase هنا يوفر قاعدة البيانات؛ تسجيل دخول محرري CMS يتم عبر Payload. لذلك حصص مستخدمي Supabase Auth ليست عدد زوار الموقع في هذه البنية.

هذه مراجعة للكود وبيانات الاستيراد في النسخة المحلية. لا تثبت حالة المحتوى أو الاستهلاك أو إعدادات الحسابات المنشورة على الإنترنت.

إدارة أكثر من موقع من Payload CMS واحد

نعم، هذا ممكن. إضافة @payloadcms/plugin-multi-tenant الرسمية تضيف ربط المستندات بموقع أو Tenant، واختيار الموقع داخل لوحة الإدارة، وفلاتر للمحتوى والعلاقات. ويمكن جعل Collection تتصرف كإعدادات عامة بسجل لكل موقع باستخدام isGlobal. يجب إنشاء Collection للمواقع وتحديد حقولها بنفسنا. توثيق الإضافة الرسمي.

مثال مبسط: موقع EnviroMET وموقع علامة أخرى لهما مدير عام واحد؛ محرر EnviroMET يرى محتوى موقعه فقط. كل موقع له دومين وهوية وصفحات وإعدادات SEO مستقلة، بينما يمكن إعادة استخدام مكونات العرض في الكود.

دعم اللغات مختلف عن دعم المواقع. العربية والإنجليزية الموجودتان الآن ترجمتان لنفس الموقع، ولا توفران عزلًا بين علامتين أو شركتين. الإضافة ليست مثبتة حاليًا، ولا توجد مجموعة Sites أو Tenants.

التغييرات المطلوبة في هذا المشروع

  1. إضافة Sites أو Tenants بحقوق محددة وحقول الاسم والدومين واللغات والهوية، وتثبيت إصدار متوافق من الإضافة مع إصدار Payload المستخدم. الوثائق الحالية قد تتضمن خصائص أحدث؛ نختبر التوافق قبل الترحيل.
  2. ربط Pages وServices وProjects وMedia وEnquiries وShared Sections وPage Templates بالموقع المناسب. مشاركة بعض القوالب بين المواقع تكون قرارًا صريحًا.
  3. تحويل Header وFooter وSite Settings وSolution Template من Globals عامة إلى Collections بإعدادات سجل لكل موقع، بدل مشاركة شعار وتنقل وإعدادات كل المواقع.
  4. تعديل slugField: حاليًا الـslug فريد على مستوى Collection بالكامل. نحتاج فهرسًا مركبًا للموقع والـslug، مع الحفاظ على قواعد تضارب الصفحات والخدمات والمشاريع داخل الموقع نفسه.
  5. تعديل src/lib/data.ts وكل الاستعلامات ليشمل الطلب الموقع الحالي، وربط الدومين المسجل بالموقع بشكل موثوق. لا يكفي اختيار الموقع في واجهة الإدارة. Payload Local API يتجاوز قواعد الوصول افتراضيًا؛ عند استخدام صلاحيات المستخدم نمرر الطلب والمستخدم وoverrideAccess: false، ومع العرض العام نحدد الموقع وحالة النشر صراحة. توثيق Local API.
  6. فصل مفاتيح الكاش وإعادة التحديث والـpreview وروابط Media والـcanonical والـsitemap لكل موقع؛ قيمة serverURL الواحدة حاليًا لن تكفي لكل الدومينات.
  7. ترحيل المحتوى الحالي إلى موقع EnviroMET افتراضيًا بعد نسخة احتياطية، ثم اختبار موقعين لهما نفس slug وصور ومحررين مختلفين، والتحقق من منع القراءة والتعديل والربط عبر المواقع، بما يشمل REST وGraphQL وLocal API.

التوصية: لو الهدف مواقع قريبة في الهيكل وتحت نفس الإدارة، ابدأ بتجربة موقعين باستخدام الإضافة الرسمية. لو كل عميل يحتاج عزل بيانات واستعادة مستقلة، نناقش النسخ المنفصلة. هذه المرحلة بحث فقط؛ لم يُغيَّر نموذج البيانات إلى Multi Tenant.

تكلفة الملفات مهمة في هذا المشروع

Vercel Blob في Pro يُحسب حسب الاستخدام ويستهلك من رصيد Vercel، ثم تُحاسب الزيادة. الأسعار الأساسية المعروضة: تخزين 0.023 USD / GB-month، وعمليات بسيطة 0.40 USD / million، وعمليات متقدمة 5 USD / million. توصيل الملفات له حساب مرتبط بالـCDN والمنطقة. مثال: تخزين 10 GB يقارب 0.23 USD قبل العمليات والتوصيل وتأثير الرصيد. الحصص المجانية الظاهرة لـHobby ليست حصة Pro مجانية إضافية. تسعير Blob.

حصة Supabase Storage لا تُستخدم حاليًا، لذلك لا تخصمها من فاتورة Blob. تكلفة PostgreSQL تتأثر بحجم المحتوى وإصداراته وطلبات CMS وخروج البيانات إلى Vercel، وليس بعدد الزيارات فقط. نحتاج قياسات تشغيل فعلية لتقدير تكلفة الجمهور والفيديوهات بدقة.

ابدأ بتنبيهات الميزانية في Vercel Spend Management وراجع Supabase Spend Cap. حد الإنفاق في Supabase لا يغطي كل البنود، مثل Compute وبعض الإضافات. لم يتم شراء أو تغيير أي اشتراك.

مراجعة SEO والتحسينات المنفذة

أهم مشكلة: كان الكود يضع noindex على اللغتين ويمنع الزحف للموقع كله. وهذا يمنع الظهور الطبيعي للمحتوى في محركات البحث عند الإطلاق، حتى مع وجود عناوين وأوصاف جيدة.

الإعدادات الموجودة أصلًا جيدة كبداية: عنوان ووصف وصورة لكل مستند، إعدادات SEO عامة، روابط قديمة يعاد توجيهها بشكل دائم، lang وRTL للعربية، وصور تدعم الأبعاد وsrcset والتحميل الكسول. لم أغيّر تصميم الموقع أو أضف مخطط مراجعات أو تقييمات غير موجودة.

روابط hreflang يجب أن تشير لترجمات موجودة وتعود لبعضها؛ لا يصح ربط كل صفحة عربية برئيسية إنجليزية كأنها ترجمتها. إرشادات Google للغات. تنفيذ metadata وsitemap يعتمد على آليات Next.js الرسمية: Metadata وSitemap.

نتائج التحقق المحلي: نجح فحص TypeScript والـlint واختبارات قواعد SEO وبناء الإنتاج. فحص HTTP مرّ على 153 رابطًا في قاعدة تجريبية منفصلة: 152 صفحة من المحتوى المبدئي وصفحة اختبار. تم التحقق من canonical واللغات ووسوم المشاركة وJSON-LD؛ كل صفحة لها H1 واحد. المسودة غير متاحة للعامة، وتفتح في المعاينة مع noindex؛ الترجمة غير الموجودة ترجع 404 ولا تُدرج في sitemap. تم أيضًا فحص إعادة توجيه رابط قديم وحماية فهرسة admin وAPI بالهيدر.

تم تصحيح الأوصاف المكررة: صفحات use-case-environmental-campaign وuse-case-remote-network وuse-case-solar-campaign وuse-case-technical-review وuse-case-water-assessment وuse-case-wind-campaign أصبحت لها أوصاف مختلفة بالعربية والإنجليزية، تعكس موضوع كل صفحة. التصحيح موجود في بيانات الاستيراد والترجمة، وتوجد معالجة للمحتوى الحالي عند عرضه إذا كان لا يزال يحمل النص القديم. أي وصف مخصص يكتبه المحرر يحتفظ بالأولوية.

مسار ترقية المحتوى المعتاد npm run upgrade أو deploy-vercel.bat يحفظ الأوصاف المصححة في سجلات CMS المنشورة التي لا توجد عليها مسودات معلقة. يتجنب التحديث نشر مسودة أو تغيير وصف مخصص. رفع الكود وحده لا يشغّل تحديث قاعدة البيانات؛ المعالجة في واجهة الموقع تضمن التصحيح الظاهر عند نشر الكود.

التغيير تقني في الكود. مراجعة الكلمات المفتاحية، وصياغة أوصاف مميزة لكل خدمة، والتأكد من جودة الترجمات، وتحسين الصور بناءً على قياسات Core Web Vitals، تظل عملًا تحريريًا وقياسيًا لاحقًا. Structured Data تساعد محركات البحث على فهم المحتوى ولا تضمن نتيجة غنية أو ترتيبًا معينًا. لم تُجرَ قياسات Lighthouse أو Core Web Vitals على موقع منشور.

خطوات الإطلاق والتحقق

  1. ضبط NEXT_PUBLIC_SERVER_URL على الدومين النهائي باستخدام HTTPS، مع التأكد من توجيه www وغير www إلى نسخة واحدة.
  2. إبقاء SEARCH_ENGINE_INDEXING=false أثناء التجهيز، وضبطه على true في بيئة الإنتاج وقت الإطلاق، ثم إعادة البناء والنشر. ملف .env.example يحتفظ بوضع التجهيز صراحة.
  3. التحقق من robots وsitemap وcanonical وhreflang والبيانات المنظمة في الصفحات الإنجليزية والعربية المنشورة، وتجربة صفحة غير موجودة للتأكد من حالة 404.
  4. تعبئة SEO لكل صفحة مهمة من لوحة Payload، ومراجعة العنوان والوصف وصورة المشاركة. الإعدادات العامة بديل احتياطي عند ترك الحقول فارغة.
  5. إضافة الدومين إلى Google Search Console وإرسال sitemap، ثم فحص الفهرسة والأداء ونتائج البحث بعد النشر.
  6. قرار Multi Website يأتي في مرحلة مستقلة بعد تحديد عدد المواقع وطبيعة عزل العملاء والدومينات وصلاحيات المحررين. البحث الحالي يوضح المسار المطلوب قبل التنفيذ.

تفاصيل التنفيذ ونتائج فحوص النسخة المحلية موجودة في docs/seo.md داخل المشروع. لم يتم نشر الموقع أو تعديل بيانات الإنتاج أو تغيير خطط الخدمات ضمن هذا العمل.
